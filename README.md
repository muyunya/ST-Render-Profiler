# ST-Render-Profiler · 渲染体检

一个只做**测量**的 SillyTavern 扩展：用真实浏览器数据回答一个问题——

> 聊天变卡，到底是 **JS 计算**（markdown 转换 / HTML 净化 / 分词）造成的，
> 还是 **浏览器的样式计算 + 布局 + 绘制** 造成的？

这个区分决定了优化方向：

| 结论 | 可用的优化手段 |
|---|---|
| **样式/布局占大头** | `content-visibility`、DOM 虚拟化。**Rust/WASM 完全帮不上忙**（wasm 碰不到布局引擎） |
| **JS 计算占大头** | 可以把 markdown 解析等热路径换成 Rust/WASM（2~5 倍） |

## 安装

SillyTavern → **扩展**（Extensions）→ **Install extension** → 粘贴本仓库地址：

```
https://github.com/muyunya/ST-Render-Profiler
```

装好后在扩展面板里出现「Render Profiler · 渲染体检」抽屉。

## 使用

1. 打开一个你**觉得卡的聊天**（楼层越多越能测出问题）
2. 展开「渲染体检」抽屉
3. 点 **开始测量（当前设置）**
   - 它会重新加载当前聊天并抓取整轮渲染数据（约 5~8 秒）
4. 想看 `content-visibility` 到底省了多少 → 点 **A/B 对比（屏外跳过 开 / 关）**
   - 它会自动跑两轮并给出百分比对比
5. 点 **复制报告** 把 JSON 发给我，我据此决定 WASM 优化目标

## 它测什么

| 指标 | 含义 |
|---|---|
| 整轮渲染 ms / 每层 ms | 重载聊天到渲染完成的总耗时 |
| **脚本耗时 vs 样式+布局耗时** | 核心结论。来自 Long Animation Frames (LoAF) API，Chromium 123+ |
| 脚本耗时归因 Top | 每个脚本来源（文件 → 函数）各花了多少毫秒 |
| 强制重排 ms | 读写布局属性（如 `scrollHeight`）导致的同步重排 |
| 滚动帧率 | 程序化来回滚动的平均 FPS、P95 帧时、掉帧数 |
| 节点数 | 楼层数 / 聊天区节点数 / 全文档节点数 |
| 分词成本 | 可选。每条消息调用分词器的耗时 |

## 实现说明

- 使用 `long-animation-frame` 性能条目（Chromium 123+，Edge/Chrome 均支持）做归因；
  不支持时自动回退到 `longtask` + 帧间隔统计。
- 只读测量：不改动酒馆行为，不发送任何数据到网络。
- 「复制报告」使用系统剪贴板，由你手动粘贴，扩展本身**不联网**。

## 已知限制

- LoAF 只在 Chromium 内核可用；Safari 下只有 longtask 与帧率数据。
- 帧率受系统负载影响，建议同一时段对比、多次取平均。
- 「重新加载聊天」会重置当前聊天的滚动位置，属正常现象。
